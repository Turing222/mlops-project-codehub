# WS2 Review — Authentication rate limiting and true client IP readiness

Date: 2026-06-08
Scope: current working-tree WS2 changes under `security-operability-baseline`, including backend auth rate limiting, SMS verify lockout, compose trusted proxy readiness, docs, tests, and work-item updates.
Method: high-recall review; candidates were gathered across line-by-line, removed behavior, cross-file tracing, reuse, simplification, efficiency, and altitude angles, then verified once with a recall-biased verifier. Only CONFIRMED / PLAUSIBLE findings are retained.

## Findings

1. [必须修复] `deploy/docker-compose.yml:170`
   问题：API 仍以 `--proxy-headers --forwarded-allow-ips "*"` 启动 Uvicorn，`request.client.host` 会先被任意 `X-Forwarded-For` 改写，之后 `RateLimiter` 的 `RATE_LIMIT_TRUSTED_PROXY_CIDRS` 检查已经来不及保护真实 peer。
   失败场景：如果 API 可直连，或前端 nginx 转发了客户端自带的 `X-Forwarded-For` 链，攻击者可以每次请求伪造不同的 forwarded IP；Uvicorn 先把 `request.client` 改成伪造值，`/sms/login` 和 `/google/callback` 的 rate-limit key 就按攻击者可控 IP 分桶，从而绕过本次新增的认证限流。
   修复建议：不要在生产 compose 中使用 `--forwarded-allow-ips "*"`；把可信代理来源限制到 compose/nginx 网段，或关闭 Uvicorn 的 forwarded header trust，只在应用层以 `RATE_LIMIT_TRUSTED_PROXY_CIDRS` + `X-Real-IP` 做受信任提取。

2. [必须修复] `backend/services/sms_service.py:99`
   问题：`stored is None`（未发送、已过期或不存在验证码）也会计入手机号维度失败次数，未认证调用方可以在没有有效 challenge 的情况下锁定任意手机号。
   失败场景：攻击者对受害者手机号直接提交 5 次 `/sms/login` 随机验证码，此时 Redis 中没有 `sms:<phone>`；每次都会增加 `sms_verify_fail:<phone>`，达到阈值后设置 `sms_verify_lock:<phone>`。受害者随后请求并输入真实验证码，也会先命中锁而收到 `SMS_VERIFY_LOCKED`。
   修复建议：只对存在验证码但内容错误的尝试累计 lockout；缺失/过期验证码返回失败但不消耗手机号锁定预算，或把锁定维度绑定到已经发出的 challenge/token。

3. [必须修复] `backend/services/sms_service.py:97`
   问题：验证码校验仍是 `GET` 后本地比较，再异步 `DELETE`，不是原子 compare-and-delete；一次性验证码在并发正确请求下可被接受多次。
   失败场景：同一手机号同一验证码有两个并发 `/sms/login` 请求，二者都在任一 `DELETE` 完成前读到相同 `sms:<phone>` 值，并都通过 `hmac.compare_digest()` 返回成功，导致同一个短信验证码签出多个登录 token。
   修复建议：用 Redis Lua 脚本或等价原子操作完成锁检查、验证码比较、删除验证码/失败状态；至少让成功路径以原子 compare-and-delete 保证单次使用。

4. [必须修复] `backend/services/sms_service.py:121`
   问题：失败计数使用分离的 `INCR` 与 `EXPIRE`，首次失败时如果 `INCR` 成功但 `EXPIRE` 前发生连接/进程故障，会留下没有 TTL 的失败计数。
   失败场景：Redis 接受 `INCR sms_verify_fail:<phone>` 后连接中断，`EXPIRE` 未执行；之后几天内零散失败会继续累加这个永久 key，最终在统计窗口之外错误锁定手机号，违背 `SMS_VERIFY_FAILURE_WINDOW_SECONDS` 语义。
   修复建议：用 Lua/transaction/pipeline 保证首次计数与 TTL 设置原子化；或者使用 `SET key 1 EX <window> NX` + 后续 `INCR` 的安全组合。

5. [必须修复] `backend/api/deps/services.py:80`
   问题：`get_sms_service()` 读取 `get_web_settings()`，而本次新增的 SMS lockout 默认值同时写入了 `configs/app/base.yaml`；`WebSettings` 只读 env/dotenv，不接入 `AppYamlSettingsSource`，因此 YAML 中的这些配置不会影响 SMSService。
   失败场景：运维在 `configs/app/base.yaml` 或 `configs/app/prod.yaml` 调整 `SMS_VERIFY_FAILURE_LIMIT` / `SMS_VERIFY_LOCKOUT_SECONDS`，聚合 `Settings()` 能读到 YAML，但运行时依赖注入创建 SMSService 时仍使用 `WebSettings` 的代码默认或环境变量，生产 abuse control 与提交的 YAML 配置不一致。
   修复建议：让 WebSettings 也接入 app YAML source，或在依赖注入中使用聚合 `settings` 的 web 字段；同时补一个覆盖 `get_sms_service()` 从 YAML 配置取值的 focused test。

6. [建议修复] `deploy/docker-compose.yml:146`
   问题：`environment.RATE_LIMIT_TRUSTED_PROXY_CIDRS: ${RATE_LIMIT_TRUSTED_PROXY_CIDRS:-}` 与 service `env_file` 重复；如果没有通过项目部署脚本传 `--env-file` 渲染 compose，显式 environment 会以空字符串覆盖 service env_file 中的模板值。
   失败场景：操作者手动在 `deploy/.env.ec2` 设置 `RATE_LIMIT_TRUSTED_PROXY_CIDRS=172.16.0.0/12`，但直接执行 `docker compose -f deploy/docker-compose.yml up`；Compose 插值不读取 service `env_file`，该字段渲染为空，API 容器内实际值覆盖为 `""`，compose fallback 下所有用户又共享 frontend proxy IP 的限流 bucket。
   修复建议：避免在 `environment` 中重复声明同名 key，或确保 compose 入口只能通过带 `--env-file deploy/.env.ec2` 的脚本执行，并在文档/脚本中显式 fail fast。
